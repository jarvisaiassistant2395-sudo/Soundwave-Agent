# Technical review — Soundwave AI, October 2026

A full pass over this tree: what to **fix**, what to **upgrade**, what to **add**.
Every finding below was reproduced or read in this checkout — no speculation, and
the raw commands are in the appendix so you can re-run them.

**What I ran here:** `server` typecheck + `npm test` (70 files, **898 passed, 2
skipped**, 73 s), `server` test-config typecheck, `frontend` `tsc --noEmit` +
`vite build` (green), the API booted against the built SPA (`WEB_DIST`), and a
scripted A/B probe against the dev proxy. `mobile/`, `desktop/` and `voiceclone/`
were reviewed by reading, not executed (Android SDK / Windows Electron not in
this sandbox).

---

## Verdict

The product is in far better shape than the average solo-built AI app, and the
hard part — the pipeline, the agent, the packaging — works. The gap is not
features. It is that **the shipped app cannot tell you when it is broken, and its
default data store can silently erase itself.** Those two, plus the usual
dependency debt, are where the next fortnight should go.

Nothing here says "rewrite". The three highest-severity items are each a handful
of lines, and two of them are already solved elsewhere in this same codebase —
they just were not applied to the oldest files.

## 1. Fix

### F1 — `JsonStore` can silently erase the user's data (critical)

`server/src/lib/store.ts` is the store for **every desktop customer** (no
`DATABASE_URL` on the desktop — `desktop/src/server-env.cjs:158-170`), and it is
the one writer in the codebase that does not do the atomic dance the rest of the
repo uses.

Three problems in 20 lines:

```ts
// store.ts:214-224
try {
  const raw = fs.readFileSync(this.file, "utf8");
  const parsed = JSON.parse(raw) as Partial<DbShape>;
  this.db = { ...emptyDb(), ...parsed };
} catch {
  this.db = emptyDb();          // ← any read/parse error becomes "brand new install"
}
this.persist();                 // ← …and 150 ms later this overwrites the file

// store.ts:226-236
this.saveTimer = setTimeout(() => {
  fs.writeFileSync(this.file, JSON.stringify(this.db), "utf8");  // ← not atomic
}, 150);
```

* The write is a direct, non-atomic, whole-file `writeFileSync`. Kill the app (or
  the machine) mid-write and `store.json` is truncated.
* If the file is ever unreadable or half-written, the `catch` swallows it and
  boots an **empty** database — then `persist()` writes that empty database over
  the file 150 ms later, destroying the evidence. The user's account link,
  projects, export jobs, API keys and invoices are gone, with no message and no
  copy.
* `catch {}` also hides permission/disk errors.

**Fix (match your own house pattern).** `lib/brain/settings.ts:91-93`,
`niches.ts:227-229`, `persona.ts:97-99`, `cache.ts:61-63`, `usage.ts:86-88`,
`geminiChats.ts:99`, `gmail.ts:131`, `emailSchedule.ts:116` and
`companion/service.ts:94` already do `tmp → rename`, `mode: 0o600`. Do the same
here, and:

1. On parse failure: rename the bad file to `store.corrupt-<ts>.json`, log
   loudly, and **refuse to start empty** (or start read-only) instead of
   clobbering it.
2. Keep rotating backups (`store.<YYYY-MM-DD>.json`, last 7) written once a day.
3. Flush on shutdown (see F5) so the 150 ms debounce is not a data-loss window.
4. Consider a `version` field now, so a future schema change has somewhere to
   hang a migration (`brain/niches.ts` already versions its file — same idea).

The rest of `dataDir` (~30 JSON files) has the same class of bug in at least
`brand.ts:154`, `briefing.ts:50` and `channelWatch.ts:89`.

### F2 — the API ships a *critical* advisory (high, 30 minutes)

`npm audit --omit=dev` in `server/`:

```
proxy-addr  1.1.0 - 2.0.7   Severity: critical
  IP spoofing via IPv4-mapped IPv6 trust subnet (GHSA-jqcg-44mw-7w3h)
qs  2.2.5 - 6.15.3          Severity: moderate   (×2 advisories)
  → body-parser 1.20.5-1.20.6 → express 4.22.2
4 vulnerabilities (3 moderate, 1 critical) — all fixable via `npm audit fix`
```

`proxy-addr` is what Express uses to evaluate `trust proxy` — and this app sets
`app.set("trust proxy", 1)` (`app.ts:40`). Fix now: `npm ci && npm audit fix`,
then re-run the suite. The dev-tree advisories (`vitest`, `esbuild`, `tinypool`)
matter less and are handled by U4.

Frontend shipping tree: `react-router` 6.x — open redirect via `<Link>` /
`useNavigate` (fix is `react-router-dom@7.18.4`, a major). Fold into U2.

### F3 — rate limiting is bypassable with one header (high)

`server/src/lib/security.ts:38-41`:

```ts
const trustIp = (req) => {
  const xff = req.headers["x-forwarded-for"];
  if (typeof xff === "string" && xff.length > 0) return xff.split(",")[0]!.trim();
  return req.ip ?? "unknown";
};
```

Every limiter keys on this (`security.ts:79, 88, 97`), including
`authSignInLimiter` (40 attempts / 15 min in production). It reads
`X-Forwarded-For` **unconditionally**, ignoring whether anything trustworthy is
in front. Anyone who can reach the port directly gets a fresh bucket per request
by rotating the header — and with `trust proxy: 1` plus the `proxy-addr`
advisory above, `req.ip` is not trustworthy either.

**Fix:** make it explicit. `TRUST_PROXY` env (`""`/`false` default → use
`req.ip` with no proxy trust; `1` or `loopback` behind Caddy/nginx in
`docker-compose.yml`), drop the hand-rolled `trustIp`, and keep the per-user key
that already exists for authenticated traffic (`security.ts:60-68`). Then the
limits mean something on a self-hosted box where the API port is reachable.

### F4 — the documented dev flow is broken for every app-local route (medium, verified)

`frontend/vite.config.ts:15` sets `changeOrigin: true`, so the proxied request
reaches Express with `Host: localhost:4000` while the browser page's `Origin` is
`http://localhost:5173`. `notFromApp()` (`middleware/localApp.ts:21-37`)
compares those two and answers:

```
$ curl -X POST http://127.0.0.1:5173/api/v1/auth/dev-session \
       -H 'Origin: http://127.0.0.1:5173' -d '{"name":"Reviewer"}'
{"error":{"code":"FORBIDDEN","message":"Not available from other sites."}}   [403]

# with changeOrigin: false (one word), same command:
{"user":{…},"signedIn":true,"development":true}                              [200]
```

So in the browser dev flow — and in any Vite preview — these are all dead:
**Settings → Brain** (where you paste the Gemini key), **Settings → Phone**,
Memory, Morning Setup, Gmail/email, the Gemini file chat, YouTube one-click, and
the dev sign-in. The packaged desktop app is unaffected (page and API share an
origin), which is why nobody has hit it: the Windows app is the only way you
have been testing, and the E2E runs there.

**Fix:** `changeOrigin: false` (verified above) *and/or* make `notFromApp()`
compare the `Origin` against `config.appUrl` plus a dev allowlist instead of the
`Host` header — the Origin comparison is the one that actually defends against a
foreign site. Add a test for both directions (`server/tests/*` can call the
middleware directly).

### F5 — no graceful shutdown (medium)

`server/src/index.ts` registers only `unhandledRejection` and
`uncaughtException`; there is no `SIGTERM`/`SIGINT` handler and nothing flushes
on the way out. Consequences: `docker compose stop` and Ctrl-C drop whatever was
in flight; the 150 ms-debounced store writes are lost; the desktop quitting right
after an action (the tray's "Quit") can lose the last mutation; in-flight
renders leave jobs that only get settled on the *next* boot (`initClips()`).

**Fix:** a shutdown path that stops the schedulers
(`briefing`, `channelWatch`, `postSchedule`, `emailSchedule`, `reminders`,
`trends`, `metering`), flushes every store, `server.close()`, and a timeout that
then exits — plus `stop_grace_period: 30s` and a container `healthcheck` in
`docker-compose.yml` (the `db` service has one; `api` does not) and a `USER
node` in `deploy/Dockerfile.api` (it currently runs as root).

### F6 — `uncaughtException` is swallowed *inside Electron's main process* (medium)

`desktop/src/main.js:975-977`:

```js
// Import the bundled server (ESM) — this starts listening on loopback.
await import(pathToFileURL(path.join(appRoot, "server", "dist", "index.js")).href);
```

The API runs **in-process** in Electron's main process. `index.ts:25-29` then
does:

```ts
process.on("uncaughtException", (error) => {
  console.error("[soundwave] Handled uncaught exception:", error);
});
```

…which is the classic footgun: the process continues after an unknown error, now
in an undefined state, with an in-memory database and a half-dead API. In the
desktop that also hides Electron main-process faults from the user entirely.

**Fix:** log it to a file (F7), then exit — and in the desktop, relaunch or show
a real error dialog. Keep "log and continue" only where it is provably safe
(e.g. a rejected promise handled at a route boundary, which the Express error
middleware already does).

### F7 — the shipped app has no logs and no crash reporting (medium, half day)

116 `console.*` calls in `server/src`, plus the desktop's own `console.log` —
all going to a stdout that does not exist in a packaged Windows GUI app. There
is no file log, no `crashReporter`, no `render-process-gone` /
`child-process-gone` hook, no "open log folder", no "copy diagnostics". When a
customer says "it stopped working", there is nothing to look at, and you cannot
see failure rates in the field at all.

**Fix:** the smallest thing that changes the game — a tiny logger that writes
JSON lines to `%APPDATA%\Soundwave AI\logs\soundwave-<date>.log` (keep 7 days),
installed before the server import so the API's existing `[soundwave]` messages
land there; hooks for `uncaughtException`, `unhandledRejection`, Electron
`crashReporter.start()`, `render-process-gone` and the renderer's `window.onerror`
forwarded over the existing preload bridge; then a **Settings → Help → Open logs
folder / Copy diagnostics** pair. This is also the prerequisite for supporting
Move 6 (retail sales) — you cannot run a paid desktop app blind.

### F8 — `requestId` is always `undefined` (medium-low, 1 hour)

`middleware/error.ts:20` defines `requestIdMiddleware`, and **nothing imports or
mounts it** (verified by grep across `server/src`). So every API error body the
client renders/logs carries `requestId: undefined`, and a 500 in the field
cannot be tied to a log line.

**Fix:** `app.use(requestIdMiddleware)` as the first middleware in `app.ts`,
echo `X-Request-Id` back, and include it in the logger's per-request line (F7,
A7). The client already surfaces it (`frontend/src/lib/api.ts`).

### F9 — a broken Postgres silently becomes an empty local store (medium-low)

`store.ts:449-462`: if `DATABASE_URL` starts with `postgres` but the connection
fails, it logs a warning and falls back to `JsonStore`. In a hosted deployment
that means the app keeps booting, keeps accepting sign-ins — into an **empty**
database — while every existing user appears to have lost their account and
projects. It also means a misconfigured deploy looks "up" to a health check.

**Fix:** in production, fail fast (fatal boot error) unless
`ALLOW_JSON_FALLBACK=1` is set explicitly; expose the store kind in
`/api/health` (and F5/A6's readiness probe) so monitoring sees it.

### F10 — three CSPs that disagree (low, 1–2 h)

| Where | Difference |
|---|---|
| `server/src/lib/security.ts:9-22` (helmet → the packaged desktop app + any server-served SPA) | strictest: no `style-src 'unsafe-inline'`; adds `style-src-attr 'none'`; `frame-ancestors 'none'` |
| `deploy/nginx.conf:17` | allows `style-src 'unsafe-inline'`; `frame-ancestors 'self'` |
| `mobile/index.html:11-12` | allows `style-src 'unsafe-inline'`, `connect-src http: https:` |

Today the desktop app *renders* fine (React writes inline styles through CSSOM,
which CSP does not cover — `setAttribute("style", …)` would be blocked, but React
does not use it), so this is not an outage. But the divergence is a trap: any
library that injects a `<style>` element at runtime (motion-dom ships a
view-transition helper that does exactly that) is silently dropped in the
packaged app and works over nginx. **Fix:** one exported CSP constant consumed by
helmet, and a check in `desktop/e2e.mjs` that fails the build on any
`Content-Security-Policy` console error during a real UI pass.

### F11 — Android permits cleartext to any host (low, 1 h)

`mobile/android/app/src/main/AndroidManifest.xml:18` sets
`android:usesCleartextTraffic="true"` app-wide. The pairing flow genuinely needs
plain HTTP to the PC on the LAN (the payload is AES-GCM inside), but it also
permits plaintext to any host. **Fix:** an `android:networkSecurityConfig` that
allows cleartext only for `localhost` and the private ranges used for pairing
(`10./172.16-31./192.168./169.254.`), everything else HTTPS-only.

### F12 — deprecated/advisory-bearing dependencies in the shipped tree (low)

* `multer@1.4.5-lts.2` — npm prints *"Multer 1.x is impacted by a number of
  vulnerabilities, which have been patched in 2.x"* on every install. 2.4.0 is
  the fix (`npm i multer@2 @types/multer@2`; the API is source-compatible for
  the disk-storage usage here).
* `react-router@6` — see F2/U2.

### F13 — four copies of the Python engine (low, ~2 h)

`soundwave-agent/viral_engine.py` (301 lines), `soundwave-agent/short_runner.py`,
`Mark-LIV/plugins/soundwave_viral_engine.py`, `mark-liii-plugins/…` and
`soundwave-agent/plugins/*` — four different hashes across the three plugin
trees, and the two `requirements.txt` files disagree (`edge-tts` exists only in
`soundwave-agent/requirements.txt`; the root one also pins `yt-dlp`). Decide
which is the product: it is the TypeScript app + the desktop shell. Either delete
the legacy Python path or reduce it to a thin client that calls the API — four
copies of the same engine will drift, and one of them will be the one a user
runs.

### F14 — binaries are downloaded without a checksum (low, 1 h)

`desktop/src/kokoro-manager.cjs:57-62` verifies **size + sha256** for every model
file it fetches — a genuinely good pattern. `scripts/download_ffmpeg.ps1` and
`scripts/download_ytdlp.ps1` fetch executables and check nothing but
`Length -gt 1000000`. There is no auto-updating code path you can lock down
completely, but at least verify yt-dlp's published `SHA2-256SUMS` (and gyan.dev's
checksum for ffmpeg) before the binary is executed.

### F15 — small drifts (low)

* README advertises desktop **1.7.0** features; `desktop/package.json` says
  **1.6.6** (mobile is 1.3.5). Either ship the bump or mark those sections "next
  release".
* README is **938 lines** — it is a manual, a spec and a marketing page in one
  file. Split it (README → quick start + links; the rest to `docs/`).
* No `LICENSE` at the root for your own proprietary code (third-party licensing
  is handled well — `THIRD-PARTY-NOTICES.txt`, `scripts/license-audit.mjs`,
  `scripts/licenses/`). A one-line `UNLICENSED`/proprietary notice file removes
  the ambiguity.

## 2. Upgrade

### U1 — Node 20 is end-of-life, and it is your release path

`node:20` appears in `.github/workflows/release-desktop.yml:45`,
`.github/workflows/shorts-trends-smoke.yml:29` and three stages of
`deploy/Dockerfile.api` (the Android workflow is already on 22; this sandbox has
22). Node 20 went EOL in April 2026 — no more security patches, and the runtime
that builds what you sell.

Do: bump those to **22** (or 24, the current Active LTS), add
`"engines": { "node": ">=22" }` to each `package.json` and a `.nvmrc` — there is
none today, so "Node 20+" in `start.sh` and the README is the only contract.

### U2 — now, low risk (~1 h)

`npm audit fix` in `server/` (F2), `react-router-dom` → 7.18 (F2), plus the patch
bumps npm already offers: `supertest`, `tsx`, `@types/ws`, `autoprefixer`,
`postcss`, `thinking-orbs`, `react-hook-form`.

### U3 — this month, single majors

`multer` 2.4 (F12), `helmet` 8, `express-rate-limit` 8, `jsdom` 30, `dotenv` 18,
`zustand` 5, `lucide-react` 1.x, `@types/node` 22/24, `@prisma/client` +
`prisma` 5.22 → 6/7 (do the client regeneration and a migration rehearsal
against a copy of the database, in its own PR). `express` stays on the 4.x line
(4.22.3 carries the security fixes); Express 5 belongs in U4.

### U4 — planned migrations, one PR each (1–2 weeks total)

Gate every one of these on: `npm run typecheck` + `npm test` (server + mobile +
desktop) + a **packaged Windows E2E run** (`desktop/e2e.mjs`) on the branch.

| Migration | From → To | Notes / real cost |
|---|---|---|
| React | 18.3 → 19.3 | `@types/react` too; legacy `ReactDOM.render` and ref-as-prop cleanups; the app is 16 pages + 60 components, mostly mechanical |
| Vite | 5.4 → 8.x | with `@vitejs/plugin-react` 6; check `manualChunks` and the dev proxy (F4) |
| react-router | 6.30 → 7.18 | already required by the security advisory |
| Tailwind | 3.4 → 4.3 | the real work: `tailwind.config.js` + `index.css` (13.6 KB) become CSS-first `@theme`; do it in one quiet week, it touches every page |
| Vitest | 2.1 → 5.x | clears the dev-tree advisories (tinypool, @vitest/mocker, esbuild) |
| zod | 3.25 → 4.x | `.default()`/`.optional()`/error-shape changes ripple through `middleware/validate.ts` and every route schema — budget a day |
| framer-motion | 11 → 14 | package rename to `motion`; the app only uses it in 6 places |
| express | 4.22 → 5.2 | optional; async error propagation improves things here, but it is the riskiest of the set against 70 test files |
| TypeScript | 5.9 → 7.0 | **hold.** It is a compiler rewrite and your toolchain (tsx, vitest, vite plugins) needs to be green on it first. Spike on a branch, no deadline. |

### U5 — make upgrades automatic

There is no `.github/dependabot.yml` or Renovate config anywhere, which is how a
tree this size reaches 20+ advisories. Add Dependabot for
`server/`, `frontend/`, `mobile/`, `desktop/` (grouped, monthly, one PR per
ecosystem) plus a CI step `npm audit --omit=dev --audit-level=high` for server
and frontend so a *shipping* advisory fails a build instead of waiting to be
noticed.

## 3. Add

### A1 — PR checks and branch protection (half a day, highest leverage)

Not one workflow here triggers on `pull_request:` (verified: `push`,
`workflow_dispatch`, one `schedule`). Tests do run — but only because
`release-desktop.yml` builds on *branch pushes*, i.e. the 30-minute Windows
release job is your unit-test gate, and a PR from a fork or a branch nobody
pushed gets no checks at all.

Add `ci.yml` on `pull_request` (and push to `main`): ubuntu, Node 22, matrixed
across the four packages —
`server`: `npm ci && npm run typecheck && npm test`; `frontend`: `npm ci && npm
run typecheck && npm run build`; `mobile`: `npm ci && npm run typecheck && npm
test`; `desktop`: `npm ci && npm test`. Then make it a required status check.
Cheap, fast, and it stops the Windows runner being the safety net.

### A2 — Lint and format (1 day including the fix sweep)

There is **no ESLint, no Prettier, no EditorConfig** in 552 tracked files. Add
ESLint 9 (flat config) + `typescript-eslint` + `eslint-plugin-react-hooks` +
Prettier, wire `npm run lint` into CI, and land the `--fix` sweep as its own
commit (the 898 tests are your safety net). The highest-value rules here:
`react-hooks/exhaustive-deps` (the app is full of effects polling services) and
`@typescript-eslint/no-floating-promises` (there are many `void`-less calls in
route handlers).

### A3 — Frontend unit tests (medium, do it with A2)

`frontend/src` is ~20 k LOC, 16 pages, 60 components — and **zero tests**
(`server` has 70 test files, `mobile` 6, `desktop` 8; `frontend/package.json`
has no `test` script at all). The packaged E2E is good but slow and
Windows-only. Add `vitest` + `@testing-library/react` + `jsdom` and start where
the bugs live, not everywhere: `lib/api.ts` (401-refresh + CSRF header),
`lib/plans.ts`, `lib/speech.ts`, `lib/agentChat.ts` (streaming), `store/auth.ts`.
One axe smoke test over `AppShell` + `AgentHub` covers most a11y regressions.

### A4 — See the field: diagnostics + opt-in error reporting (with F7)

Right now there is no signal about *any* installed copy: version mix, crash rate,
which feature fails. Add: the local log file (F7), a **Send diagnostics** bundle
(version, OS, log tail, store kind, ffmpeg/Gemini status — no keys, no file
contents), and opt-in crash reporting (Sentry or self-hosted GlitchTip) with a
clear consent switch in Settings. A one-line anonymous "version started" ping is
worth more than it sounds for knowing whether an update actually rolled out.

### A5 — Data safety and backup (medium)

Beyond F1's atomic writes: automatic daily rotation of `store.json` (keep 7),
**Export my data** (zip the data dir minus secrets) and **Restore** in Settings →
Help, and a documented `pg_dump` cron/companion for the hosted edition. The
desktop app holds someone's memory, drafts, schedules and channel plans — losing
that is losing the product.

### A6 — Container / production hardening (small)

`deploy/Dockerfile.api`: `USER node`, `HEALTHCHECK` hitting `/api/health`, and
`.github`-verified digest pinning for `postgres:16-alpine` / `caddy:2-alpine`;
`docker-compose.yml`: `healthcheck` + `stop_grace_period` for `api` (see F5), and
`restart: unless-stopped` is already right. Add `/api/ready` that checks the
store and the ffmpeg probe (F9), so a broken deploy fails readiness instead of
serving.

### A7 — Observability-lite (small, with F7/F8)

Replace the ad-hoc `console.*` with a tiny structured logger (pino or a 40-line
wrapper): one line per API request with method, path, status, duration and
request id; one line per job stage transition; a counter for render failures per
stage. That is enough to answer "why was it slow / what failed" in the field
without a metrics stack.

### A8 — Frontend performance and structure (medium)

One 510 KB entry chunk + 164 KB vendor + 115 KB motion, and `App.tsx` imports
all 16 pages eagerly — no `React.lazy` anywhere (verified). Add route-level code
splitting plus a bundle budget in CI, and split the two monsters while you are
there: `pages/AgentHub.tsx` (**3,839 lines**) and `pages/Settings.tsx` (1,190).
That split is also what makes A3 possible on those pages.

### A9 — Accessibility and motion (small)

The UI is animation-heavy (orb visualizer, framer-motion, progress bars). Respect
`prefers-reduced-motion`, keep focus rings and keyboard paths through the modals
and tabs (`components/ui/Modal.tsx`, `Tabs.tsx`), and add the axe smoke from A3.
For a desktop app sold to non-technical creators this is cheap credibility.

### A10 — Update integrity, in the right order

`desktop/electron-builder.yml` documents `verifyUpdateCodeSignature: false`
until the certificate exists — that sequencing is correct. Until then, keep the
sha512 verification electron-updater does from `latest.yml`, and make update
failures visible in the UI (the state machine in `desktop/src/update.cjs` already
tracks `error`). The day the cert arrives: flip the flag, set `publisherName`,
and bump the installer to a signed release. Also add a Windows SmartScreen /
macOS-notarization note to `docs/RELEASING.md` once signed — it is already the
best doc in the repo.

### A11 — Phone release track (small)

`android-companion.yml` already signs when the keystore secrets exist; add an
AAB target and an internal-track upload so the companion stops being
sideload-only, and fill in the Play data-safety form (the app records audio and
talks to a PC on the LAN — both need declaring).

## 4. What is already strong — do not churn these

* **Test discipline.** 898 server tests across 70 files, mobile and desktop unit
  tests, plus a packaged-app E2E on a real Windows runner that exercises the mic,
  whisper.cpp, the voice bar, the tray and the clip pipeline. That is better than
  most funded teams ship.
* **The desktop security posture.** `contextIsolation: true`, `nodeIntegration:
  false`, `sandbox: true` on every window, `setWindowOpenHandler` +
  `will-navigate` locks, `restrictPermissions()`, loopback-only bind
  (`BIND_HOST=127.0.0.1`), no `asar` for the server tree but a protected core
  (`docs/PROTECTING_THE_CODE.md`), `asInvoker` installs (no UAC).
* **Secrets hygiene.** No `.env`, keys, or credentials in the tree; `.gitignore`
  is thorough; test fixtures use obviously fake `AIzaSy…` values.
